# Mobile apps: iPhone and Android (Capacitor)

Written 12 October 2026 for the founders. Plain words first, commands at the end.

**What this is.** The same Build Your Pillars website code, wrapped in a thin native shell (Capacitor 8) so it can be installed from an app store or from a file. The web files are packed inside the app, so it opens with no signal. The shell adds the things a website cannot do: a daily reminder, Android back-button handling, and (optionally) reading steps, sleep, exercise and water from Apple Health or Health Connect.

**Honest status.** This work was done on a Mac with no Xcode, no Android SDK and no Java. So the native projects were **created and synchronised**, but **not compiled and not run on any phone or simulator**. Compiling is set up to happen in the cloud (GitHub Actions, section 6). Until that has run green once, treat "it builds" as unproven.

## 2. What the founders must do

1. **Confirm the app ID `com.buildyourpillars.app`.** It is a placeholder. It is the iPhone "bundle ID" and the Android "package name", and **it cannot be changed after the first upload to either store**; changing it later means a brand-new listing with no reviews or users. If you want something else (for example `ca.impactarts.byp`), say so before anyone uploads. To change it before the first upload: `capacitor.config.ts` (`appId`), then `android/app/build.gradle` (`namespace`, `applicationId`), the Java folder `android/app/src/main/java/...`, `android/app/src/main/res/values/strings.xml`, and the Xcode bundle identifier.
2. **Apple Developer Program** (US$99 a year). Individual is fastest; organisation needs a D-U-N-S number. See `docs/store-apps-plan.md` section 2 (that file is in the main folder, not yet on this branch).
3. **Google Play Console.** The plan found that Google may require an **Organization** account for health apps, and an organisation needs a D-U-N-S number (Google says up to 30 days). Ask Play support whether a wellness tracker counts, and keep the reply. See `docs/store-apps-plan.md` section 3.
4. **Signing keys** (cannot be made by Claude and must never be committed):
   - Android: an upload keystore (`.jks`). Make it once, back it up in two places (Box and a password manager). Losing it is painful.
   - iPhone: a distribution certificate and provisioning profile, which Apple creates once the account exists.
   - Later these go into GitHub secrets (names suggested in the header of `.github/workflows/mobile-ios.yml`). None exist yet.
5. **Privacy policy page at https://buildyourpillars.com/privacy.** Both stores require a working link, and Health Connect shows the same page. The app already points Health Connect at that address (`android/app/src/main/res/values/strings.xml`).
6. **Before the first store submission** (from `docs/store-apps-plan.md`, not part of this work): in-app account deletion, an in-app link to the privacy page, an opt-in screen before the first AI reflection, a demo login for reviewers, screenshots.
7. **Decide whether to turn on "Import from Health"** for the first release (section 5). Turning it on adds Apple's and Google's health reviews. The reminder and offline use alone are enough for a first release if you want to move faster.
8. **Set two GitHub variables** so the cloud builds work: repository Settings, Secrets and variables, Actions, **Variables**: `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (the publishable key only, never the service_role key). These are public by design; they are variables, not secrets. Optional: `VITE_HEALTH_IMPORT` set to `on`.

## 3. Why Apple should not call this "just a website" (guideline 4.2)

Apple's 4.2 asks for features "beyond a repackaged website". This app has real ones:

1. **Works fully offline.** The whole app is inside the install and (with the offline-first web work) saves and syncs later. A website in a frame cannot do that.
2. **A genuine native feature: an opt-in daily reminder** using the phone's own notification system, with a plain, health-free message.
3. **Apple Health import** (read only, optional, flagged) is the strongest, but needs the extra review.

Say all three in the review notes. This is judgement, not a guarantee; see the risk table in `docs/store-apps-plan.md`.

Also for whoever owns those areas:
- **Service worker.** Inside the app the files are local, so the service worker adds nothing and can serve stale files after an app update. Skip registering it when `isNative()` (from `src/lib/native/platform.ts`) is true.
- **Offline queue / sync.** Use the Capacitor Network plugin only if the web events (`online`/`offline`) prove unreliable on a phone; not installed, not needed yet. Foreground/background hooks are in `NativeShell`.
- **Sign-in links in emails** (confirm email, reset password) open in the phone's browser, not the app, because deep links are not set up. People can still return to the app and sign in. Proper deep links need a Supabase redirect URL and `appUrlOpen` handling: a later task.
- **Notches and gesture bars.** Android uses Capacitor's default safe-area handling (padding added for you). On iPhone `contentInset: 'automatic'` is set. If the header looks cramped on a real phone, add `viewport-fit=cover` to `index.html` and `env(safe-area-inset-*)` padding.

## 4a. The reminder, exactly

- **Off by default.** Nothing is asked until the person flips the switch.
- Before the phone's permission box appears, our own screen explains it ("Before your phone asks") with **Continue** and **Not now**.
- Text of the notification: title **Build Your Pillars**, body **A gentle nudge to notice your day**. A test fails if it ever mentions health, numbers, streaks or goals.
- Chosen time, once a day. It is **inexact** on purpose (a few minutes late is fine) so Google Play's exact-alarm restriction does not apply; the exact-alarm permission is removed in the Android manifest.
- Handles "granted", "denied" (explains how to allow it in the phone's Settings) and "not asked yet".
- The reminder lives only inside the phone's own notification system. Nothing is stored in our database or in browser storage.

## 5. Import from Health: what it does, and what you must test on a phone

**What it does.** When the person taps **Import from Health** (phone app only, flag on), the phone asks permission (its own screen), the app reads the **last 14 full days** (not today) of steps, sleep, exercise minutes and water, shows a list, and asks **"Add 14 days? You can edit or delete them any time."** Only on **Add** does it save to the person's own `habit_logs`. It only fills blanks: a number the person already logged is never replaced, and running it twice is harmless. It reads only; nothing is written to Apple Health or Health Connect. Nothing is used for advertising (Apple 5.1.3).

**Plugin chosen: `@capgo/capacitor-health` 8.11.10.** MPL-2.0 licence (fine to use unmodified; changes to the plugin's own files would have to be shared). Maintained (frequent releases, 8.x matches Capacitor 8). Vendor-backed by Capgo. One plugin covers HealthKit and Health Connect. Mood is **not** supported by it, so mood, energy, stress and check-ins stay in the app only. The other health plugins in the plan are stale or weaker.

**Findings from reading the plugin that changed what was built:**
- Its Android manifest asks for about 45 health permissions (read and write, blood pressure, heart rate and more). Google Play requires you to justify each one and only ask for what you use, so **the app manifest removes all but four reads**: steps, sleep, exercise sessions, hydration. The Play Console "Health Connect" declaration must list exactly these four.
- Its local-notification sibling adds an exact-alarm permission Google restricts. Removed (section 4a).
- The plugin needs Android 8 (API 26) or newer, so the app's minimum is 26, not Capacitor's default 24. Android 7 phones cannot install it. That is a small share of phones, but worth knowing for "elderly users with older phones".
- The plugin and Gradle build need Java 21 (the CI uses 21).

**Android source value.** Rows from Health Connect are saved with `source = 'manual'`. The database only allows `apple_health` or `manual`. Giving Health Connect its own value (for example `health_connect`, so the dashboard can show rings) needs a new migration, which was deliberately not written here.

**Wording and the privacy policy.** The iPhone permission text and Health Connect wording say: read only, only when you tap, only those four things, last 14 days, saved only to your own account, never advertising. Check these against the final privacy policy (`docs/gdpr-compliance.md`): Health data is "special category" data and needs the explicit consent step described there. Also: **iCloud must not store health data** (Apple 5.1.3); this app does not use iCloud.

**Day boundaries.** Steps and water use the phone's daily totals (the phone already removes double counting between phone and watch). Sleep follows the same rules as the existing file importer: asleep stages only, credited to the day you wake (6 pm boundary), one source per night, the Watch preferred. Zero is treated as "not logged", never saved as 0.

**Test on a real phone before turning the flag on (the code has never run there):**
1. iPhone: tap Import, the Health sheet appears listing exactly four types, then the preview. Compare 2 or 3 days with the Health app.
2. iPhone: deny one type; the app must still show the others.
3. Android with Health Connect: same. On an Android 13 or older phone, check the "Install Health Connect" message.
4. Check day totals line up with local midnight (the plugin groups by local day; this was read from its source, not tested).
5. Import twice; the second time must say nothing new to add.
6. Edit an imported day in Log; it must save.

**What to declare in the stores.** Apple: Health and Fitness data collected, linked to the person, for app functionality, not tracking. HealthKit capability needed in Xcode (the entitlement file is already in place). Google Play: Health Connect declaration with the four reads; Health apps declaration; Data safety form. Details: `docs/store-apps-plan.md` sections 2 and 3.

## 6. Cloud builds (GitHub Actions)

Both workflows pin every action to a full commit hash, give each job only `contents: read`, and use no secrets. The repo is private, so only people with repo access can download artifacts.

- **Android: `.github/workflows/mobile-android.yml`.** Runs on **Run workflow** and on any tag starting `app-v` (for example `app-v0.1.0`). Builds a **debug APK** and uploads it as artifact `build-your-pillars-debug-apk` (kept 14 days). It is a test build, not for the Play Store.
- **iPhone: `.github/workflows/mobile-ios.yml`.** **Run workflow** only (macOS minutes cost about ten times more). Compiles unsigned for the Simulator and unsigned for a real iPhone (compile check) and uploads the Simulator app. It cannot make an installable iPhone app: signing needs Apple credentials that do not exist yet (listed in the file header as TODO).

How to run: GitHub, the repo, **Actions** tab, pick the workflow on the left, **Run workflow**, wait about 10 minutes, open the finished run, **Artifacts** at the bottom.

## 8. Build it yourself

### On a Mac with Xcode (iPhone)
1. Install Xcode 26 or newer from the App Store, open it once, accept the licence (`sudo xcodebuild -license accept` in Terminal), and install the iOS platform when asked.
2. In the project folder: `npm ci`, then `npm run build`, then `npx cap sync ios`. (No CocoaPods needed: the project uses Swift Package Manager. It looks for the plugins in `node_modules`, so `npm ci` must be run first.)
3. `npx cap open ios` opens Xcode. Pick a Simulator at the top and press Play to run.
4. For a real iPhone or TestFlight: click the **App** target, **Signing & Capabilities**, choose your team, confirm the bundle ID, and check that the **HealthKit** capability is listed (only keep it if you ship the health import). Then **Product, Archive**.

### With Android Studio (Android)
1. Install Android Studio (2025.2.1 or newer). It brings Java and the Android SDK; let it install API 36.
2. `npm ci`, `npm run build`, `npx cap sync android`, then `npx cap open android`.
3. Wait for Gradle to finish, pick an emulator or a plugged-in phone (USB debugging on), press Play.
4. A debug APK from the command line: `cd android && ./gradlew assembleDebug` (needs Java 21). The file appears at `android/app/build/outputs/apk/debug/app-debug.apk`.

## 9. How an Android tester installs a debug APK

1. On GitHub: repo, **Actions**, **Mobile Android debug APK**, open the latest green run, download **build-your-pillars-debug-apk** (a zip; unzip it to get `app-debug.apk`). The tester must have access to the private repo.
2. Send the APK to the phone (email to self, Drive, USB cable).
3. On the phone, tap the file. Android asks to allow installs from that app ("Install unknown apps"): allow it for just that app, then **Install**. A "Play Protect" notice may appear for an unfamiliar app: tap **Install anyway**.
4. Open Build Your Pillars. To update, install the newer APK over the top. To remove: long-press the icon, **Uninstall**.

**Later, a download from the website.** Once a **signed release APK** exists (it needs the keystore from section 2), host it at `https://buildyourpillars.com/downloads/BuildYourPillars-1.0.0.apk` (put the file in `public/downloads/` of the website only at that point; **no APK is committed now**), with a plain page that tells people how to allow the install. Before offering this to the public, check Google's developer-verification rules for sideloaded apps, which Google has been phasing in during 2026 (my recollection, not verified here).

## 10. Dependency and risk notes

- `npm audit` after install: 7 findings. **Existing before this work:** `vitest` (critical, via `tinypool` and `@vitest/mocker`; development only) and `source-map-js` (high; build tool only; `npm audit fix` can fix it). **New with this work:** `@capacitor/cli`, via `xcode`, via `uuid` (moderate, command-line tool for developers only; it never ships inside the app; the fix Capacitor offers is a downgrade to 8.4.3, which was not applied). Nothing in the packages that ship inside the app was flagged.
- `@capgo/capacitor-health` is the highest-change dependency: daily releases, MPL-2.0, one vendor. Pinned to the exact version. Re-read its release notes before upgrading.
- `android:allowBackup` is set to false so the app's local data (including the signed-in session) is not copied into Android cloud backups.
- `ITSAppUsesNonExemptEncryption` is set to false in the iPhone settings (the app only uses the phone's standard HTTPS). Confirm this answer in App Store Connect.
